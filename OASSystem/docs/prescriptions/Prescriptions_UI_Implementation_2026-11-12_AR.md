# تنفيذ واجهة الوصفات البصرية وفق الصور المعتمدة

**التاريخ:** 2026-11-12  
**المسار:** `/sales/prescriptions`  
**المرجع:** `approved-prescription-list.png` و`approved-prescription-new.png`.

## التغييرات المنفذة

- إبقاء شريط النظام العام والشريط الجانبي كما هما؛ وضع تبويبات الوصفات بجوار عنوانها في المساحة العلوية، مع «الكل» غير قابل للإغلاق، وتبويبات منفصلة للوصفات الجديدة والمحفوظة، وتأكيد إغلاق التغييرات غير المحفوظة باستخدام منطق مساحة العمل الموجود.
- إعادة تصميم قائمة الوصفات في جدول RTL يعرض رقم الوصفة والعميل والطبيب/الفاحص والعيادة والتاريخ والإصدار الحالي والحالة؛ جميع القيم مصدرها API فعلي.
- أربع بطاقات بيانات **حقيقية**: إجمالي الوصفات، إجمالي إصدارات القياسات، المسودات، الملغاة. لم نستخدم حالة «منتهية» لأن النموذج لا يحوي تاريخ انتهاء؛ ولا توجد أرقام تخمينية أو إحصاءات من الصفحة المحملة فقط. يتم حساب جميع الأعداد على الخادم حتى لو كانت القائمة مقسمة صفحات.
- تفعيل تصفية حالة الوصفة على الخادم، وتوسيع البحث ليشمل رمز الوصفة واسم/رقم العميل والطبيب والعيادة. يمنع ذلك وهم البحث المحلي على أول صفحة.
- نموذج «وصفة جديدة» يستخدم فقط الحقول الموجودة في البيانات: الكود المحجوز، العميل، تاريخ الوصفة، الطبيب/الفاحص، العيادة، الملاحظات، وتاريخ السريان وسبب الإصدار ثم حقول OD وOS: SPH وCYL وAxis وADD وPrism وPrism Base وPD وMonocular PD وVA وFitting Height وملاحظات العين.
- إظهار القياسات في جدول يقارن العين اليمنى باليسرى، واستبدال بطاقات الإصدارات الطويلة بسجل جانبي قابل لاختيار إصدارات محفوظة وقراءة قياساتها التاريخية.
- جعل العميل للقراءة فقط عند تعديل وصفة محفوظة لأن عقد التحديث لا يسمح بنقل الوصفة إلى عميل آخر.
- عرض الأخطاء المحلية بجوار قياسات خاطئة مع حد أحمر ومنع محاولة الحفظ حتى تصحيحها؛ تبقى قواعد التحقق الخادمية نهائية.
- إضافة استعلام مستندات مرتبطة حقيقي يعتمد على معرف الإصدار في رؤوس الطلبات والفواتير وبنودها. الوصول لهذه النتائج مشروط بصلاحيات قراءة الوصفات وطلبات العملاء والفواتير، ولا تُعرض مستندات مُختلقة في غيابها.
- إضافة `orderId` إلى المسار الحالي لصفحة طلبات العملاء لدعم فتح المستند المرتبط مباشرة، دون تغيير مسارات سابقة.
- تحديث الستايل في CSS المشترك باستخدام ألوان/سطوح متغيرة مع الثيم، وتحسين التباين والخطوط والشاشات الصغيرة.

## القيود والتنبيهات

- **لا يوجد في النموذج الحالي خيار مستقل لحفظ وصفة جديدة كمسودة**؛ عند حفظ الوصفة مع الإصدار الأول تتحول إلى نشطة وفق `PrescriptionMapper`. لم تتم إضافة زر «حفظ كمسودة» لأنه سيكون مضللًا دون تعديل قواعد العمل.
- البحث باسم العميل يستعين باستعلام عملاء على الخادم ثم يربطه بمعرفات الوصفات؛ ينبغي اختبار الأداء مع أعداد ضخمة من العملاء والاسم الشائع.
- لا يمكن الحكم على نجاح البناء أو اتصال قاعدة البيانات من فحص الشيفرة وحده. **لم يُشغَّل `dotnet build` أو اختبارات SQL Server في بيئة إعداد الحزمة بسبب عدم توفر SDK.**

## قائمة تحقق تشغيلية قبل الاعتماد

1. بناء الحل كاملًا: `dotnet restore` ثم `dotnet build OASSystem.sln --no-restore` (استخدم اسم الحل الموجود فعليًا إن اختلف).
2. فتح `/sales/prescriptions` والتأكد من أن مؤشرات API تعرض أعدادًا صحيحة تتجاوز سجلات الصفحة الحالية.
3. البحث بالرمز وباسم عميل موجود خارج الصفحة الأولى، وتغيير حالة الوصفة، والعودة إلى نتائج كاملة بعد حذف الفلتر.
4. فتح وصفتين والتحرك بينهما، وإنشاء وصفة جديدة؛ تأكد من عدم تكرار تبويب الوصفة نفسها ومن ظهور رسالة عند إغلاق تعديلات غير محفوظة.
5. حفظ إصدار أول به قياسات صحيحة؛ تحقق من فتح تبويب رقم الوصفة ومن إنشاء قيود قياسات العينين حسب API.
6. إدخال Axis بقيمة تتجاوز 180 وPD غير موجب والتأكد من ظهور رسالة تحت الحقل وعدم إرسال طلب الحفظ.
7. إنشاء إصدار جديد ومقارنة القيم المحفوظة السابقة دون تغيير تاريخ الفواتير أو قياساتها المرجعية.
8. التحقق من المستندات المرتبطة لمستخدم لديه صلاحيات القراءة كاملة، وآخر لديه صلاحية قراءة الوصفات فقط.
9. تجربة ثيم سماء وشمس والوضع المظلم، وعرض 1366px وعرض هاتف؛ التأكد من القراءة والتمرير الأفقي داخل جدول القياسات فقط.
