# تقرير تنفيذ تبويبات إتمام البيع والمدفوعات — OASSystem

**التاريخ:** 13 نوفمبر 2026  
**النسخة الأساسية:** OASSystem_Checkout_Full_Project_2026-11-13.zip  
**النطاق:** صفحة `/sales/checkout` ومكوناتها فقط؛ دون تغيير قواعد الترحيل أو قاعدة البيانات.

## التعديلات المنفذة

1. نقل تبويبات صفحة إتمام البيع إلى جهة اليمين في شريط العنوان، واستبدال تبويب «الطلبات» بتبويب ثابت «بيع جديد».
2. فتح تبويب مستقل بعنوان «إتمام بيع — رقم الطلب» عند اختيار الطلب، ومنع تكراره عند إعادة اختياره، وإتاحة الإغلاق مع التحذير من الدفعات غير المنفذة. يحتفظ كل تبويب بنموذج الدفعات محليًا أثناء التنقل بين التبويبات داخل الصفحة.
3. إضافة زر «فتح الطلب في طلبات العملاء» أسفل منطقة الإجراءات، وينقل مباشرة إلى `/sales/customer-orders?orderId=...`.
4. إظهار «المدفوع سابقًا» من `PaymentSummary.PaidAmount + PaymentSummary.AppliedAdvanceAmount` بدل الاكتفاء بـ«المدفوع الآن». وإظهار المدفوع المباشر والعربون المطبق والمتاح بشكل منفصل، لتجنب جمع العربون المتاح مرتين.
5. إضافة زر «تأكيد الدفعة» لكل سطر: التحقق من العملة والحساب والمبلغ، ثم معاينة الصرف من الخادم. يتم إلغاء التأكيد إذا عدل المستخدم السطر، ويُمنع «إتمام البيع» قبل تأكيد جميع السطور أو إلغائها.
6. **التأكيد ليس تحصيلًا فعليًا:** الدفعة المعتمدة داخل النموذج لا تنشئ سند قبض؛ تنشأ المعاملة فقط عند نجاح إتمام البيع.
7. عند وجود فاتورة على الطلب، يظهر المدفوع السابق والمتبقي من ملخص الفاتورة ويُمنع مسار إتمام البيع المكرر. ويمكن استخدام رابط «تحصيل دفعة للفاتورة» الذي يفتح `/sales/invoices?invoiceId=...&collect=true` عندما يوجد رصيد مستحق.
8. أُبقي استخدام المفتاح الفريد المحلي لكل تبويب عند إعادة المحاولة، وتغيير المفتاح بعد العملية الناجحة.

## التحقق والاختبارات المطلوبة

- فحص ساكن لتطابق أسماء أحداث المكونات والخصائص واكتمال بنية HTML وتفسير CSS.
- التحقق من سلامة أرشيفات ZIP وتطابق الملفات المعدلة مع المشروع الكامل.
- **لم يُنفذ `dotnet build` أو تشغيل SQL Server وBlazor** في البيئة الحالية؛ لا يجوز اعتبار النسخة مجتازة للبناء أو اختبارات التكامل.
- اختبر يدويًا: تبويب «بيع جديد» ثابت على اليمين، فتح طلبين والتبديل بينهما دون فقد الدفعات، إغلاق تبويب فيه بيانات غير منفذة، ظهور المدفوع بعد وجود فاتورة، تحصيل دفعة لفاتورة مرحلة، تأكيد دفعة ثم تعديلها، إدخال دفعة بعملة مختلفة، والعربون الذي يغطي كامل المستحق.
- **خطر قائم خارج نطاق هذا التعديل:** ضمان منع تكرار الإتمام عبر خوادم متعددة أو بعد فقد الاتصال يحتاج إلى اختبار التزامن/المفتاح الفريد الدائم في قاعدة البيانات.
