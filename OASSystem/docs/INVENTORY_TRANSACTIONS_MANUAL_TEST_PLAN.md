# Inventory V1 — Inventory Transactions UI Manual Test Plan

## الهدف
اختبار واجهة `/inventory/transactions` يدويًا قبل الانتقال إلى واجهة حركات المخزون، والتأكد من أن الإدخال الخاطئ لا يسبب Exception أو Blazor circuit failure، وأن العملية تنتقل كاملة UI → API → DB، ثم عند Post تنتقل آثارها بصورة صحيحة إلى InventoryBalance وInventoryLedger داخل Transaction واحدة.

## نطاق V1 لأنواع العمليات
الواجهة تعرض الأنواع التالية فقط:
1. رصيد افتتاحي `Opening`
2. إدخال مخزون `Receipt`
3. إخراج مخزون `Issue`
4. تحويل بين المخازن `Transfer`
5. تعديل زيادة `AdjustmentIncrease`
6. تعديل نقص `AdjustmentDecrease`
7. مرتجع شراء `PurchaseReturn`
8. مرتجع بيع `SalesReturn`
9. تالف / Scrap `Scrap`

`ProductionIssue` موجود في الـEnum الداخلي لكنه ليس ضمن UI V1 الحالية، ولا نضيف له شاشة أو خيارًا جديدًا في هذه المرحلة.

## معيار التحقق المرئي المشترك
لكل حقل إجباري:
- [ ] توجد نجمة حمراء `*` بجانب Label.
- [ ] عند الحفظ بدون قيمة يظهر حد/توهج أحمر حول الحقل.
- [ ] تظهر رسالة صغيرة تحت الحقل: `هذا الحقل إجباري.` أو رسالة أكثر تحديدًا.
- [ ] يظهر Snackbar عام: `هناك بيانات إجبارية لم يتم إدخالها.`.

لكل حقل اختياري قابل للكتابة:
- [ ] لا توجد نجمة حمراء.
- [ ] يظهر `(اختياري)` في Placeholder عندما يكون الحقل فارغًا.

للقيم غير الصحيحة:
- [ ] الخطأ يظهر على الحقل نفسه.
- [ ] Snackbar يطلب مراجعة الحقول الحمراء.
- [ ] لا يحدث unhandled exception ولا يتوقف البرنامج.

## 1) التحميل والقائمة والفلاتر
- [ ] فتح الصفحة بدون أخطاء.
- [ ] جميع العمليات تظهر، وليس أول 200 سجل فقط.
- [ ] البحث برقم العملية يعمل.
- [ ] البحث بالسبب والملاحظات واسم المخزن يعمل.
- [ ] فلتر نوع العملية يعمل لكل الأنواع الظاهرة.
- [ ] فلتر الحالة `Draft / Posted` يعمل.
- [ ] فلتر المخزن يطابق مخزن المصدر أو الوجهة.
- [ ] اختيار صف يجلب تفاصيل العملية وكل البنود.
- [ ] كمية البند المعروضة تظهر بـ3 منازل عشرية، والتكلفة والإجمالي بمنزلتين.
- [ ] عملية قديمة مرتبطة بمخزن أو Variant غير نشط ما زالت تعرض بياناتها ولا تكسر الصفحة.

## 2) الحقول العامة عند الإنشاء
- [ ] `نوع العملية` مطلوب وقيمة Enum صحيحة.
- [ ] `تاريخ العملية` مطلوب؛ حذف التاريخ ثم حفظ يظهر خطأ موضعي على التاريخ.
- [ ] `السبب` اختياري للأنواع العادية وحده الأقصى 500 حرف.
- [ ] `ملاحظات` اختيارية وحدها الأقصى 1000 حرف.
- [ ] رقم العملية لا يطلب من المستخدم ويتم توليده تلقائيًا بصيغة `TXN-YYYY-######`.
- [ ] بعد الحفظ تكون الحالة `Draft`.
- [ ] زر Post متاح فقط عند اختيار عملية Draft.
- [ ] زر Post غير متاح لعملية Posted.

## 3) الحقول الديناميكية حسب نوع العملية

### Opening — رصيد افتتاحي
- [ ] يظهر `إلى مخزن` فقط، وهو مطلوب.
- [ ] لا يظهر `من مخزن`.
- [ ] الحفظ بدون المخزن يمنع الطلب ويظهر الخطأ على الحقل.

### Receipt — إدخال مخزون
- [ ] يظهر `إلى مخزن` فقط، وهو مطلوب.
- [ ] لا يظهر `من مخزن`.

### Issue — إخراج مخزون
- [ ] يظهر `من مخزن` فقط، وهو مطلوب.
- [ ] لا يظهر `إلى مخزن`.

### Transfer — تحويل
- [ ] يظهر `من مخزن` و`إلى مخزن` وكلاهما مطلوب.
- [ ] اختيار نفس المخزن في الحقلين يضع خطأ أحمر على الحقلين ويمنع الحفظ.
- [ ] اختيار مخزنين مختلفين يسمح بالحفظ.

### AdjustmentIncrease — تعديل زيادة
- [ ] يظهر `إلى مخزن`.
- [ ] `سبب التعديل` يصبح إجباريًا وتظهر النجمة الحمراء.
- [ ] ترك السبب فارغًا يظهر الخطأ الموضعي + Snackbar البيانات الإجبارية.

### AdjustmentDecrease — تعديل نقص
- [ ] يظهر `من مخزن`.
- [ ] `سبب التعديل` إجباري.

### PurchaseReturn — مرتجع شراء
- [ ] يظهر `من مخزن` فقط.

### SalesReturn — مرتجع بيع
- [ ] يظهر `إلى مخزن` فقط.

### Scrap — تالف
- [ ] يظهر `من مخزن` فقط.

### تبديل النوع أثناء الإدخال
- [ ] التحويل من نوع يحتاج Source إلى نوع لا يحتاجه يمسح Source القديم.
- [ ] التحويل من نوع يحتاج Destination إلى نوع لا يحتاجه يمسح Destination القديم.
- [ ] لا تُرسل مخازن مخفية من نوع سابق بالخطأ.

## 4) بنود الأصناف
لكل بند:
- [ ] Product Variant مطلوب.
- [ ] لا تظهر في قائمة الإنشاء Variants غير النشطة.
- [ ] لا يظهر Variant إذا كان المنتج الأب غير نشط أو `IsStockItem = false`.
- [ ] Quantity مطلوبة وأكبر من صفر.
- [ ] Quantity تقبل حتى 3 منازل عشرية `decimal(18,3)`.
- [ ] `1.234` مقبول.
- [ ] `1.2345` مرفوض برسالة موضعية.
- [ ] `0` مرفوض.
- [ ] قيمة سالبة مرفوضة.
- [ ] نص غير رقمي لا يسبب Exception ويظهر كقيمة غير صحيحة.
- [ ] قيمة تتجاوز 15 رقمًا صحيحًا في Quantity مرفوضة قبل API.
- [ ] Unit Cost مطلوبة و>= 0.
- [ ] Unit Cost تقبل منزلتين فقط `decimal(18,2)`.
- [ ] `12.34` مقبول.
- [ ] `12.345` مرفوض برسالة موضعية.
- [ ] تكلفة سالبة مرفوضة.
- [ ] قيمة تتجاوز 16 رقمًا صحيحًا في Unit Cost مرفوضة.
- [ ] إذا كان `Quantity × UnitCost` يتجاوز `decimal(18,2)` الخاص بـTotalCost يتم رفض البند قبل الإرسال.
- [ ] إضافة أكثر من بند تعمل.
- [ ] زر حذف البند يعمل عندما توجد عدة بنود.
- [ ] لا يمكن حذف البند الوحيد.
- [ ] تكرار نفس Product Variant في بندين يظهر خطأ على البنود المكررة ويمنع الحفظ.

## 5) Create Round-trip — UI → API → DB → UI
نفّذ مرة واحدة على الأقل لكل نوع من الأنواع التسعة:
1. [ ] أنشئ العملية بقيم مميزة.
2. [ ] سجّل رقم العملية الذي تم توليده.
3. [ ] تأكد أن Snackbar النجاح يظهر.
4. [ ] شغّل `scripts/verify-inventory-transactions.sql` وضع رقم العملية في `@TransactionNumber`.
5. [ ] تأكد أن Header في DB يطابق النوع والتاريخ والمخازن والسبب والملاحظات والحالة Draft.
6. [ ] تأكد أن جميع البنود موجودة بنفس Variant/Quantity/UnitCost.
7. [ ] تأكد أن `TotalCost` صحيح بالدقة المخزنة.
8. [ ] قبل Post يجب ألا يوجد Ledger لهذه العملية.
9. [ ] اضغط Refresh في UI وأعد فتح العملية.
10. [ ] قارن كل القيم المعروضة بالقيم المخزنة في DB.

## 6) Post — عمليات الوارد
ينطبق على:
- Opening
- Receipt
- SalesReturn
- AdjustmentIncrease

لكل نوع:
- [ ] سجل رصيد Variant في المخزن قبل Post.
- [ ] نفّذ Post.
- [ ] Status يصبح `Posted = 2`.
- [ ] `PostedAtUtc` و`PostedBy` يتم تعبئتهما.
- [ ] لكل Line يوجد Ledger واحد `MovementType = In`.
- [ ] `QuantityIn = Line.Quantity` و`QuantityOut = 0`.
- [ ] OnHand يزيد بمقدار الكمية.
- [ ] Average Cost وInventoryValue يتغيران وفق moving average.
- [ ] إعادة فتح العملية في UI يعرض الحالة مرحّلة والبنود صحيحة.
- [ ] زر Post يصبح غير متاح بعد الترحيل.

---

## 7) Post — عمليات الصادر
ينطبق على:
- Issue
- PurchaseReturn
- AdjustmentDecrease
- Scrap

مع وجود رصيد كافٍ:
- [ ] لكل Line يوجد Ledger واحد `MovementType = Out`.
- [ ] `QuantityOut = Line.Quantity` و`QuantityIn = 0`.
- [ ] OnHand ينقص بمقدار الكمية.
- [ ] تكلفة Ledger للصادر تعتمد متوسط التكلفة الحالي عندما يكون موجودًا.
- [ ] Status يصبح Posted.

### رصيد غير كافٍ — حالة إلزامية
1. أنشئ Issue أو Scrap بكمية أكبر من OnHand.
2. [ ] Create ينجح كـDraft (لأن الرصيد يُفحص عند Post).
3. [ ] Post يفشل بإشعار واضح عن عدم كفاية الرصيد.
4. [ ] لا يتوقف البرنامج ولا يغلق Blazor circuit.
5. [ ] Status يبقى Draft.
6. [ ] لا يتم إنشاء أي Ledger للعملية.
7. [ ] لا يتغير InventoryBalance.
8. إذا كانت العملية تحتوي عدة بنود وكان أول بند صالحًا والثاني غير كافٍ:
   - [ ] يتم Rollback للعملية كلها.
   - [ ] لا يبقى Ledger للبند الأول.
   - [ ] لا يتغير رصيد البند الأول.

هذه النقطة تختبر `TransactionBehavior` وAtomicity وليست مجرد UI validation.

---

## 8) Post — Transfer
- [ ] قبل Post سجّل رصيد Variant في المخزن المصدر والوجهة.
- [ ] بعد Post ينخفض المصدر بنفس Quantity.
- [ ] يزيد المخزن الوجهة بنفس Quantity.
- [ ] مجموع OnHand بين المخزنين لا يتغير بسبب التحويل نفسه.
- [ ] لكل Line يوجد **سجلان** في Ledger: Out للمصدر وIn للوجهة.
- [ ] تكلفة الإدخال إلى الوجهة تأتي من تكلفة المخزون المصدر المستخدمة في التحويل.
- [ ] عند نقص رصيد المصدر يفشل Post بالكامل بدون حركة جزئية في الوجهة.

---

## 9) الحماية من الحالات غير المتوقعة
- [ ] قطع API أثناء Load يظهر Feedback ولا يوقف التطبيق.
- [ ] قطع API أثناء Save يظهر Feedback ولا يترك الشاشة في Loading دائم.
- [ ] قطع API أثناء Select يظهر Feedback ولا يوقف التطبيق.
- [ ] قطع API أثناء Post يظهر Feedback ولا يترك زر الترحيل في Loading دائم.
- [ ] نقر Save سريعًا عدة مرات لا ينشئ أكثر من عملية بسبب `_saving`.
- [ ] نقر Post سريعًا عدة مرات لا يرحّل مرتين بسبب `_posting` + حالة السيرفر.
- [ ] محاولة Post لعملية Posted عبر API تُرفض ولا تنشئ Ledger مكررًا.

---

## 10) البيانات المرجعية غير المتاحة
- [ ] إذا لم يوجد أي مخزن نشط يظهر تنبيه واضح داخل نموذج الإنشاء.
- [ ] إذا لم يوجد أي Product Variant نشط يظهر تنبيه واضح.
- [ ] المخازن غير النشطة لا تظهر كخيار لعملية جديدة.
- [ ] الـVariants غير النشطة لا تظهر كخيار لبند جديد.

---

## شرط إغلاق اختبار واجهة عمليات المخزون
لا ننتقل إلى واجهة Inventory Ledger حتى:
- جميع أنواع V1 التسعة تم اختبار Create عليها.
- تم اختبار Post للوارد والصادر والتحويل.
- تم اختبار insufficient stock والـrollback متعدد البنود.
- جميع أخطاء الحقول تظهر موضعيًا بدون crash.
- UI وDB يعرضان نفس القيم بعد Round-trip.
- لا توجد قيمة يقبلها Application ثم ترفضها SQL بسبب Length/Precision معروف.
- لا يوجد partial posting عند حدوث خطأ.
